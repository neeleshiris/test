1. Interview Opening Answer - 60 Seconds

Best answer: Authentication verifies the identity of the caller, and authorization decides what that authenticated caller can access. In ASP.NET Core, authentication is handled through authentication schemes such as JWT Bearer, Cookie, or OpenID Connect. The selected scheme validates the token or cookie and creates a ClaimsPrincipal. After that, authorization checks roles, claims, policies, or resource-specific rules. In real projects, I use JWT Bearer for APIs/SPAs, Cookie authentication for MVC/Razor apps, OAuth/OIDC for enterprise identity, client credentials or managed identity for service-to-service, and policy/resource-based authorization for fine-grained business access.

One line: Authentication answers “Who are you?”, Authorization answers “Are you allowed to do this?”

2. Simple Mental Model

Office Security Example

  • Authentication: Security guard checks your ID card at building entrance.
  • Authorization: Even after entering building, your card may allow only 3rd floor, not server room.
  • Scheme: Different ways to identify you — ID card, biometric, visitor pass.
  • Role: Employee, Manager, Admin.
  • Claim: Department=Finance, Region=India, Permission=ApprovePayment.
  • Policy: Only Finance Managers can approve payment above 1 lakh.
  • Resource-based authorization: You can access only your own locker/document/order.

3. Request Pipeline - What Actually Happens

Client sends request
  |
  |-- Authorization: Bearer JWT token OR Cookie
  v
Authentication middleware
  |
  |-- Chooses scheme: Bearer / Cookie / OIDC
  |-- Validates token/cookie
  |-- Creates ClaimsPrincipal
  v
Authorization middleware
  |
  |-- Checks [Authorize]
  |-- Checks role / claim / policy / resource rule
  v
Controller action executes OR API returns 401/403

How to explain in interview

When a request reaches ASP.NET Core, authentication middleware runs first. It validates the incoming credential using configured scheme. If valid, it creates HttpContext.User as ClaimsPrincipal. Then authorization middleware checks whether this user satisfies endpoint rules like roles, claims, policies or resource ownership.

401 vs 403

  • 401: Token missing, invalid, expired. User identity is not established.
  • 403: Token valid, user authenticated, but permission is insufficient.

4. Scheme-Based Authentication - Clear Explanation

Q. What is a scheme?

A scheme is a named authentication mechanism. It tells ASP.NET Core how to authenticate the request. Examples are Bearer for JWT token, Cookies for cookie login, and OpenIdConnect for external identity provider login.

Real Project Scenario

Suppose one application has:

  • Admin MVC portal using cookie login.
  • Angular frontend calling APIs using JWT Bearer token.
  • External login using Microsoft Entra ID / OIDC.

In this case, we configure multiple schemes and select which scheme should authenticate which endpoint.

Minimal Code to Remember

[Authorize(AuthenticationSchemes = "Bearer")]
public IActionResult ApiEndpoint() { return Ok(); }

[Authorize(AuthenticationSchemes = "AppCookie")]
public IActionResult AdminDashboard() { return View(); }

When to use scheme-based auth?

  • When same application supports JWT and Cookie both.
  • When some endpoints should accept only JWT, not cookies.
  • When admin UI and public API have different authentication methods.
  • When MFA or external provider uses a separate scheme.
Interview line: Scheme-based auth is useful when the app has multiple authentication mechanisms and we want endpoint-level control over which handler should authenticate the request.

5. JWT - What to Explain, Not Just Code

JWT Lifecycle

  1. User logs in.
  2. Server validates credentials.
  3. Server creates JWT with claims.
  4. Client sends JWT in Authorization header.
  5. API validates signature, issuer, audience, expiry and key.
  6. API creates ClaimsPrincipal.
  7. Authorization checks role/claim/policy.

What JWT Contains

  • Header: algorithm and token type.
  • Payload: claims like userId, email, role, permission, tenantId.
  • Signature: proof that token was not modified.

Important Interview Clarity

JWT payload is not encrypted by default. It is Base64Url encoded and can be decoded. Do not put passwords, secrets, PAN, Aadhaar, credit card, or sensitive data inside JWT.

Minimal Code to Remember

app.UseAuthentication();
app.UseAuthorization();
[Authorize]
public IActionResult SecureApi() { return Ok(); }

7. Real Project Examples for 10 Years Experience

Example 1: E-commerce Application

Scenario: Customer, Seller and Admin use same platform.

  • Customer can view only own orders.
  • Seller can manage only own products.
  • Admin can manage all users and products.

What to use:

  • JWT Bearer for API authentication.
  • Role-based auth for Admin/Seller/Customer.
  • Resource-based auth for own orders/products.
  • Policy for special permissions like refund approval.
Interview line: For own data access, role alone is not enough. I check resource ownership also.

Example 2: HRMS / Leave Management System

Scenario: Employees apply for leave. Manager approves leave. HR can view HR data.

  • Employee can apply leave.
  • Manager can approve leave only for their team.
  • HR can view employee records.

What to use:

  • JWT or Cookie depending on SPA/MVC.
  • Policy: CanApproveLeave.
  • Claims: Department, ManagerId, Permission.
  • Resource check: leave request belongs to manager's team.

Example 3: Banking / Payment System

Scenario: APIs are sensitive and require stronger security.

  • Customer can view own account.
  • Operations team can view transactions.
  • High-value transaction approval needs special permission/MFA.

What to use:

  • OIDC/OAuth from trusted identity provider.
  • Short-lived access tokens.
  • Refresh token rotation.
  • Policy-based authorization for high-value operations.
  • Audit logging for every sensitive action.

Example 4: Microservices

Scenario: Order Service calls Payment Service and Inventory Service.

  • User-to-API call uses delegated user token.
  • Service-to-service call uses client credentials / managed identity.
  • Each service validates token independently.

What to use:

  • JWT Bearer token validation in each API.
  • Client credentials for background/service calls.
  • Scopes/permissions for service-level access.
  • Correlation ID and audit logs.

8. OAuth, OIDC and JWT - Interview Clarity

OAuth 2.0Authorization frameworkDelegated API access

Which flow to use?

  • Authorization Code + PKCE: SPA/mobile app login.
  • Client Credentials: service-to-service communication.
  • Refresh Token: get new access token without login again.
One-liner: JWT is what the token looks like; OAuth/OIDC define how token is issued and used.

9. Security Checklist - What Senior Candidate Should Mention

  • Use HTTPS always.
  • Validate issuer, audience, lifetime, signature and signing key.
  • Keep access token short-lived.
  • Use refresh token rotation and revocation.
  • Store secrets in Key Vault / environment variables / secret manager.
  • Do not log tokens, passwords or refresh tokens.
  • Never store passwords in plain text; use hashing and salt.
  • Use policy-based authorization for complex permissions.
  • Use resource-based check for own-data access.
  • Use rate limiting on login and sensitive APIs.
  • Use audit logs for sensitive operations.
  • Apply least privilege principle.
Risk signal: Long-lived JWT, missing issuer/audience validation, secrets in appsettings/source code, role-only access for own data, no refresh token strategy.

10. Common Mistakes Interviewer May Catch

  • Confusing authentication with authorization.
  • Saying JWT is encrypted by default.
  • Not knowing 401 vs 403.
  • Putting sensitive data in JWT payload.
  • Using only role-based auth for every problem.
  • Not explaining schemes when app has cookie + JWT.
  • Wrong middleware order.
  • Not mentioning token expiry and refresh token.
  • Not mentioning secret storage.

11. Interview Q&A - Speak Like Senior Developer

Q1. How do you secure an ASP.NET Core API?

I configure JWT bearer authentication, validate issuer, audience, signing key and lifetime, use HTTPS, apply [Authorize], then use role/policy/resource-based authorization based on endpoint need. I also use short-lived tokens, refresh token rotation, Key Vault for secrets, logging without sensitive data and audit logs for critical operations.

Q2. Why policy-based authorization?

Role-based authorization is simple but not enough for complex enterprise rules. Policy-based authorization centralizes rules and can combine roles, claims and custom logic. Example: only HR Manager with ApproveLeave permission can approve leave.

Q3. What is scheme-based auth?

It means selecting which authentication handler should process the request. For example, APIs may use Bearer JWT while MVC pages use cookies. We can select scheme using [Authorize(AuthenticationSchemes="Bearer")] or through policies.

Q4. How would you secure own-order access?

First authenticate user using JWT. Then fetch order from DB and compare order.UserId with logged-in user id claim. Admin can bypass if role allows. This is resource-based authorization because decision depends on actual order data.

Q5. JWT vs OAuth?

JWT is token format. OAuth is framework for delegated authorization. OIDC is identity/login layer over OAuth. In real systems, token should usually be issued by trusted identity provider using OAuth/OIDC.

Q6. What do you validate in JWT?

Signature, issuer, audience, expiry/lifetime, signing key and claims required by business rules.

12. Final Cheat Sheet

  • AuthN: identity check.
  • AuthZ: permission check.
  • Scheme: named auth handler like Bearer/Cookie/OIDC.
  • ClaimsPrincipal: authenticated user object in ASP.NET Core.
  • JWT: token format with claims and signature.
  • Role: broad access group.
  • Claim: user attribute or permission.
  • Policy: reusable authorization rule.
  • Resource-based: access depends on actual data.
  • 401: not authenticated.
  • 403: authenticated but not allowed.
Final closer: I do not use one authorization approach everywhere. I choose based on use case: roles for simple admin/user access, claims and policies for fine-grained enterprise rules, resource-based checks for ownership, schemes for multiple auth mechanisms, and OAuth/OIDC for trusted identity and token issuance.
