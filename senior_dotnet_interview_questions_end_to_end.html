1. Production Debugging & Error Finding

Q1. If something breaks in production Web API on Azure, how will you find where the error is?

Senior Answer

I follow a structured approach. First, I check Application Insights for failed requests, exceptions, response codes, dependency failures, and correlation ID. Then I verify the same API from Postman or browser network tab to check status code, payload, headers, and response body. After that, I check App Service logs, Log Stream, and deployment logs if the issue is related to startup or deployment. If the issue is still unclear, I reproduce locally with the same configuration or use remote debugging carefully in non-production/staging. Finally, I identify root cause, fix it, add logs/alerts, and document prevention steps.

Interview line: “I don’t directly jump to code. I first isolate whether it is client-side, API-side, dependency-side, configuration-side, or deployment-side.”

Q2. What do you check first for HTTP 500 error?

For HTTP 500, I first check Application Insights exceptions and failed requests. I look for stack trace, request URL, operation ID/correlation ID, and dependency failures like SQL timeout or external API failure. Then I check recent deployment/config changes, environment variables, connection strings, and App Service Log Stream.

Q3. API is working locally but failing on Azure. What can be the reason?

  • Wrong app settings or connection string in Azure Configuration.
  • Missing Key Vault permission or Managed Identity issue.
  • Different environment variable or ASPNETCORE_ENVIRONMENT value.
  • Firewall/network restriction for database or external service.
  • Deployment package mismatch or missing files.
  • CORS issue if frontend calls API.

Q4. API is slow in production. How will you troubleshoot?

I check Application Insights performance blade to find slow endpoints. Then I inspect dependencies to see whether latency is from database, external API, cache, or application code. I check SQL query duration, N+1 queries, missing indexes, thread pool starvation, excessive logging, large payloads, and synchronous blocking calls. If needed, I add custom telemetry around critical code paths.

Q5. Browser shows CORS error. How do you debug?

I check browser console and network tab for preflight OPTIONS request. Then I verify API CORS policy: allowed origins, methods, headers, credentials, and middleware order. In ASP.NET Core, UseCors should be configured correctly before authorization endpoints where required.

Q6. How do you use correlation ID?

A correlation ID uniquely tracks a request across services. We generate or accept a correlation ID from headers and log it in every service, database operation, and external dependency call. In microservices, it helps trace the complete request flow from API Gateway to downstream services.

Q7. What is remote debugging and when do you use it?

Remote debugging means attaching Visual Studio debugger to an Azure App Service process to debug deployed code. I use it only when logs and telemetry are not enough, preferably in dev/staging because it can impact performance. I ensure the deployed code and symbols match the local code.

Q8. How do you handle an intermittent issue?

I add more diagnostic logs with correlation ID, capture request parameters safely, check dependency failures and retry patterns, monitor time-based trends, and compare with deployment/configuration changes. For intermittent failures, I also check transient network errors, SQL deadlocks, throttling, and race conditions.

2. ASP.NET Core Web API

Q9. Explain request pipeline in ASP.NET Core.

ASP.NET Core request pipeline is a sequence of middleware components. Each middleware can process the request, call the next middleware, and process the response. Common middleware includes exception handling, HTTPS redirection, routing, CORS, authentication, authorization, and endpoint mapping.

app.UseExceptionHandler("/error");
app.UseHttpsRedirection();
app.UseRouting();
app.UseCors("DefaultPolicy");
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

Q10. Difference between middleware and filters?

Middleware works at the application pipeline level for all requests. Filters are MVC-specific and run around controller/action execution. Middleware is good for global cross-cutting concerns like logging, exception handling, authentication. Filters are good for action-level validation, authorization, and result transformation.

Q11. How do you handle exceptions globally?

I use global exception handling middleware or UseExceptionHandler. The middleware logs the exception and returns a consistent error response without exposing internal stack trace to clients.

app.UseExceptionHandler(errorApp =>
{
    errorApp.Run(async context =>
    {
        context.Response.StatusCode = 500;
        context.Response.ContentType = "application/json";
        await context.Response.WriteAsJsonAsync(new
        {
            message = "An unexpected error occurred.",
            traceId = context.TraceIdentifier
        });
    });
});

Q12. How do you version Web APIs?

Common approaches are URL versioning like /api/v1/reports, header versioning, query string versioning, or media type versioning. For public APIs, URL or header versioning is commonly used. I also maintain backward compatibility and deprecate old versions gradually.

Q13. What are idempotent APIs?

An idempotent operation gives the same result even if called multiple times. GET, PUT, DELETE are generally idempotent. POST is usually not idempotent unless we implement idempotency keys. This is important for retry handling and distributed systems.

Q14. How do you secure Web API?

  • Use HTTPS.
  • Use JWT/OAuth2/OpenID Connect for authentication.
  • Use role/claim-based authorization.
  • Validate input and avoid over-posting.
  • Store secrets in Key Vault.
  • Use rate limiting and logging.

Q15. Difference between AddScoped, AddTransient, and AddSingleton?

Transient creates a new instance every time. Scoped creates one instance per request. Singleton creates one instance for the application lifetime. For EF Core DbContext, Scoped is typically used.

3. Azure App Service & Cloud

Q16. What Azure hands-on do you have?

If your actual experience is deployment only, answer honestly but strongly:

“I have hands-on experience deploying .NET Web APIs to Azure App Service and managing application configuration. I have used/understood Application Insights for monitoring. I am currently strengthening practical knowledge on Key Vault, Service Bus, and microservices communication.”

Q17. How do you deploy Web API to Azure App Service?

I create an App Service, configure runtime stack, set app settings/connection strings, deploy via Visual Studio/Azure DevOps/GitHub Actions, enable Application Insights, verify health endpoint, and monitor logs after deployment.

Q18. What are deployment slots?

Deployment slots allow us to deploy new versions to a staging slot and then swap with production. It reduces downtime and risk. Slot-specific settings can be used for environment-specific configuration.

Q19. What is Managed Identity?

Managed Identity provides an Azure-managed identity for an application so it can access Azure resources like Key Vault without storing credentials in code or configuration.

Q20. How do you manage configuration in Azure?

I use App Service Configuration for non-secret settings, Key Vault for secrets, environment-specific settings for dev/test/prod, and avoid storing secrets in appsettings.json.

4. Application Insights & Logging

Q21. What do you check in Application Insights?

  • Failures: exceptions and failed requests.
  • Performance: slow endpoints.
  • Dependencies: SQL, HTTP, storage calls.
  • Live Metrics: real-time traffic and failures.
  • Transaction Search: request trace using operation ID.

Q22. Are all logs available only in Application Insights?

No. Application Insights is primary and centralized, but we can also check App Service Log Stream, file system logs, Kudu, deployment logs, browser console/network tab, and custom logs depending on issue type.

Q23. How do you write logs in .NET?

private readonly ILogger<ReportController> _logger;

public ReportController(ILogger<ReportController> logger)
{
    _logger = logger;
}

_logger.LogInformation("Report request started for UserId: {UserId}", userId);
_logger.LogError(ex, "Error while generating report for UserId: {UserId}", userId);
Never log sensitive data like passwords, tokens, full connection strings, or personal data.

5. Azure Key Vault

Q24. What is Azure Key Vault?

Azure Key Vault is used to securely store and manage secrets, keys, and certificates. Example: database connection strings, API keys, certificates, encryption keys.

Q25. How do you read/write secrets from Key Vault?

First create Key Vault and store secrets. Then enable Managed Identity for the app and grant required permissions like Get/List/Set. In code, use Azure SDK SecretClient with DefaultAzureCredential.

var client = new SecretClient(
    new Uri("https://your-vault.vault.azure.net/"),
    new DefaultAzureCredential());

KeyVaultSecret secret = await client.GetSecretAsync("DbConnection");
string connectionString = secret.Value;

await client.SetSecretAsync("ApiKey", "secret-value");

Q26. If you have not worked on Key Vault, how to answer honestly?

“I have not implemented Key Vault directly in production, but I understand its purpose. It stores secrets securely, and applications access it using Managed Identity and Azure SDK after proper RBAC/access policy permission.”

6. Microservices

Q27. What are microservices?

Microservices architecture divides an application into small, independently deployable services. Each service owns its business capability and can communicate with other services using REST/gRPC or asynchronous messaging.

Q28. Monolith vs Microservices?

In monolith, all modules are deployed as one application. In microservices, services are independently deployable and scalable. Microservices improve scalability and team autonomy but add complexity in communication, monitoring, deployment, and data consistency.

Q29. How will you convert Insurance Reporting Hub into microservices?

I would identify business capabilities and split them into services like User Service, Report Service, Assignment Service, Notification Service, and Audit Service. Report Service handles report metadata and generation. Assignment Service handles user-report mapping. Notification Service sends email/messages asynchronously. API Gateway exposes a single entry point. Application Insights provides distributed tracing.

Q30. How do services communicate?

  • Synchronous: REST/gRPC when immediate response is required.
  • Asynchronous: Queue/Topic using Service Bus/Kafka when decoupling and reliability are required.

Q31. What is API Gateway?

API Gateway is a single entry point for clients. It handles routing, authentication, rate limiting, request transformation, and sometimes aggregation. In Azure, API Management can act as API Gateway.

Q32. What are common microservices challenges?

  • Distributed tracing and monitoring.
  • Data consistency across services.
  • Network failures and retries.
  • Service discovery/configuration.
  • Deployment and versioning complexity.

Q33. What is circuit breaker?

Circuit breaker prevents repeated calls to a failing dependency. If failures cross a threshold, the circuit opens and calls fail fast for some time. This protects system resources and improves resilience.

Q34. How do you handle data consistency in microservices?

For distributed systems, we avoid distributed transactions where possible. We use eventual consistency, Saga pattern, outbox pattern, and idempotent consumers to make message processing reliable.

7. Azure Service Bus / Messaging

Q35. What is Azure Service Bus?

Azure Service Bus is a managed messaging service used for asynchronous communication between applications or microservices. It supports queues and topics/subscriptions.

Q36. Queue vs Topic?

Queue is point-to-point messaging where one consumer processes a message. Topic is publish-subscribe where multiple subscribers can receive the same message based on subscriptions/filters.

Q37. Why use messaging instead of direct API call?

Messaging decouples services, improves reliability, handles traffic spikes, and allows retry/dead-letter handling. It is useful when immediate response is not required.

Q38. What is dead-letter queue?

Dead-letter queue stores messages that cannot be processed successfully after retries or due to validation/processing errors. We monitor DLQ and reprocess/fix messages after root cause analysis.

8. Security & Authentication

Q39. JWT authentication flow?

User authenticates with identity provider. The provider issues a JWT token. Client sends token in Authorization header. API validates issuer, audience, signature, expiry, and claims. Then authorization is applied based on role/claims.

Q40. Authentication vs Authorization?

Authentication verifies who the user is. Authorization verifies what the user is allowed to do.

Q41. How do you protect sensitive data?

  • Use HTTPS.
  • Store secrets in Key Vault.
  • Use encryption at rest and in transit.
  • Mask sensitive logs.
  • Apply least privilege access.

9. Performance & Scalability

Q42. How do you improve Web API performance?

  • Use async/await for I/O operations.
  • Optimize SQL queries and indexes.
  • Use caching for frequently accessed data.
  • Reduce payload size and use pagination.
  • Avoid N+1 queries.
  • Use Application Insights to identify bottlenecks.

Q43. What is caching and where do you use it?

Caching stores frequently used data to reduce database/API calls. We can use in-memory cache for single instance, distributed cache like Redis for multiple instances, and response caching for cacheable API responses.

Q44. How do you scale Azure App Service?

Scale up means increasing CPU/RAM of the instance. Scale out means increasing number of instances. For high traffic, scale out with autoscale rules based on CPU, memory, request count, or custom metrics.

10. SQL / EF Core

Q45. How do you troubleshoot slow SQL query?

I check execution plan, missing indexes, table scans, joins, parameter sniffing, blocking/deadlocks, and query duration. From application side, I check EF generated SQL, N+1 queries, and unnecessary data loading.

Q46. What is optimistic concurrency?

Optimistic concurrency assumes conflicts are rare. We use row version/timestamp to detect whether data changed before update. If conflict occurs, we handle it gracefully.

Q47. Repository pattern: good or bad?

Repository pattern abstracts data access logic and improves testability. But with EF Core, DbContext already acts like repository/unit of work, so extra repository should be used only when it adds real value, not blindly.

11. CI/CD & Deployment

Q48. Explain CI/CD pipeline for .NET API.

CI builds the code, restores packages, runs tests, performs static checks, and publishes artifacts. CD deploys the artifact to target environment using approvals and environment-specific configuration. After deployment, smoke tests and monitoring validation are performed.

Q49. What is rollback strategy?

Rollback strategy means quickly reverting to a stable version if deployment fails. We can use deployment slots, previous artifacts, database backward compatibility, feature flags, and automated health checks.

Q50. What is blue-green deployment?

Blue-green deployment uses two environments: current live and new version. After validating the new version, traffic is switched. It reduces downtime and allows quick rollback.

12. Testing

Q51. Unit test vs integration test?

Unit test validates a small piece of code in isolation using mocks. Integration test validates multiple components together such as API + database or API + external service.

Q52. How do you test Web API?

  • Unit test services/business logic.
  • Integration test controllers and DB interactions.
  • Use Postman/Newman for API test collections.
  • Validate authentication/authorization scenarios.
  • Run smoke tests after deployment.

13. Design Patterns & SOLID

Q53. Explain SOLID principles.

  • S: Single Responsibility — one class should have one reason to change.
  • O: Open/Closed — open for extension, closed for modification.
  • L: Liskov Substitution — derived classes should replace base classes safely.
  • I: Interface Segregation — avoid forcing clients to depend on unused methods.
  • D: Dependency Inversion — depend on abstractions, not concrete classes.

Q54. Which patterns have you used?

Common patterns in .NET projects are Dependency Injection, Repository, Factory, Strategy, Adapter, Mediator/CQRS, and Unit of Work. Explain patterns with your actual project example.

Q55. What is dependency injection?

Dependency Injection provides required dependencies from outside instead of creating them inside the class. It improves loose coupling, testability, and maintainability.

14. System Design Scenarios

Q56. Design a reporting system like Insurance Reporting Hub.

I would design modules/services for user management, report metadata, report assignment, report generation, notification, and audit. APIs would be secured using JWT. Report generation can run asynchronously using queue/background worker for large reports. Metadata and assignments go to SQL. Generated files can be stored in Blob Storage. Application Insights tracks failures/performance. Key Vault stores secrets.

Q57. Design notification system.

API publishes notification request to queue/topic. Notification worker consumes message and sends email/SMS. Failed messages are retried and moved to dead-letter queue if repeatedly failing. Templates are stored separately. Logs and correlation IDs are used for tracing.

Q58. How will you design audit logging?

Audit log should capture who did what, when, from where, and what changed. It should be append-only. Sensitive fields should be masked. For high-scale systems, audit events can be sent asynchronously to a queue and stored separately.

15. Senior/Lead Behavioral Questions

Q59. How do you handle production incident?

I first assess impact and severity, communicate status to stakeholders, check telemetry/logs, identify mitigation, apply hotfix/rollback if required, monitor recovery, and then do RCA with preventive actions.

Q60. How do you guide junior developers?

I help with code reviews, design discussions, debugging approach, documentation, and pair programming. I focus on explaining why something is done, not just what to change.

Q61. What if you do not know a technology asked in interview?

Answer honestly but show understanding and learning ability. Example: “I have not implemented it directly, but I understand the concept and how it fits in architecture. I can quickly pick it up because I have worked on similar integration patterns.”
