1. How to Answer in Interview for Best Impression

For 10+ years experience, interviewer expects practical production-level thinking, not only textbook definitions.

Best Answer Pattern:
1. Give short definition.
2. Explain where you used it in production.
3. Mention performance/scalability impact.
4. Give small code example or real scenario.
5. Mention trade-off / when not to use.
Example line: “In production APIs, I avoid loading unnecessary data. I keep the query as IQueryable, apply filters at database level, use projection, AsNoTracking for read-only scenarios, pagination for large data, and validate generated SQL/execution plan when performance issue comes.”

2. LINQ Core Concepts

LINQ means Language Integrated Query. It allows querying objects, collections, XML, DataSet, SQL/EF data using C# syntax.

Types / Usage Areas

  • LINQ to Objects: In-memory collections like List, Array.
  • LINQ to Entities: Entity Framework queries against database.
  • LINQ to XML: Query XML documents.
  • LINQ to SQL: Older ORM approach, mostly replaced by EF/EF Core.

Syntax Types

// Query syntax
var result = from u in users
             where u.IsActive
             select u.Name;

// Method syntax - commonly used in production
var result2 = users.Where(u => u.IsActive)
                   .Select(u => u.Name);
Interview बोलने के लिए: “I mostly use method syntax in production because it is more composable for dynamic filters, paging, projection and reusable query extensions.”

3. IQueryable vs IEnumerable

PointIQueryableIEnumerable
ExecutionDatabase/provider sideIn memory
NamespaceSystem.LinqSystem.Collections.Generic
ExpressionUses expression treeUses delegates/iteration
Best ForEF/database queriesAlready loaded collection
Short Answer: IQueryable builds SQL and executes at DB level. IEnumerable works on in-memory data after data is loaded.
// Good: filtering happens in SQL
IQueryable<User> query = context.Users.Where(x => x.IsActive);
var data = query.Where(x => x.City == "Delhi").ToList();

// Risk: ToList loads data first, then filter runs in memory
IEnumerable<User> users = context.Users.ToList();
var data2 = users.Where(x => x.City == "Delhi").ToList();
What to say: “If dataset is large, I keep it as IQueryable until all filters, sorting, projection and pagination are applied. I materialize it only at the end using ToListAsync or FirstOrDefaultAsync.”

4. Deferred vs Immediate Execution

Deferred Execution

Query is not executed when it is written. It executes when we iterate or materialize it.

var query = context.Users.Where(x => x.IsActive); // Not executed yet
var list = query.ToList(); // SQL executes here

Immediate Execution

Operators like ToList, Count, Any, First, Single execute query immediately.

var count = context.Users.Count(x => x.IsActive); // Executes now
var exists = context.Users.Any(x => x.Email == email); // Executes now
Common Mistake: Calling ToList too early causes full data load and later filters run in memory.

5. Tracking vs NoTracking / AsNoTracking

Tracking

By default EF tracks entities. It keeps original and current values so SaveChanges can detect modifications.

var user = context.Users.First(x => x.Id == id);
user.Name = "Updated Name";
context.SaveChanges(); // EF knows what changed

AsNoTracking

AsNoTracking disables change tracking for read-only queries. It reduces memory usage and improves read performance.

var users = context.Users
                   .AsNoTracking()
                   .Where(x => x.IsActive)
                   .ToList();
Short Answer: Tracking is useful for update scenarios. NoTracking is best for read-only APIs, reports and list screens.
What to say: “For read-heavy APIs, I use AsNoTracking because I don’t need EF change tracker. But for update flows, I avoid AsNoTracking or explicitly attach entity if required.”

AsNoTrackingWithIdentityResolution

Useful when you want no tracking but duplicate entity instances should be resolved in result graph.

var orders = context.Orders
    .AsNoTrackingWithIdentityResolution()
    .Include(o => o.Customer)
    .ToList();

6. Pagination - How It Improves Performance

Pagination fetches limited rows instead of full dataset. It reduces DB load, memory usage, network transfer and API response time.

Offset Pagination

int page = 2;
int size = 10;

var data = await context.Users
    .AsNoTracking()
    .OrderBy(x => x.Id) // must for stable paging
    .Skip((page - 1) * size)
    .Take(size)
    .Select(x => new UserDto { Id = x.Id, Name = x.Name })
    .ToListAsync();

Pagination with Total Count

var query = context.Users.AsNoTracking().Where(x => x.IsActive);

var total = await query.CountAsync();
var items = await query.OrderBy(x => x.Id)
                       .Skip((page - 1) * size)
                       .Take(size)
                       .ToListAsync();

return new { total, page, size, items };

Keyset Pagination / Seek Pagination

Better for very large tables because it avoids huge Skip cost.

var items = await context.Users
    .AsNoTracking()
    .Where(x => x.Id > lastSeenId)
    .OrderBy(x => x.Id)
    .Take(size)
    .ToListAsync();
What to say: “For normal grids I use Skip/Take with OrderBy. For very large datasets or infinite scroll, I prefer keyset pagination using last seen Id/CreatedDate for better performance.”

7. Projection - Very Important Senior Topic

Projection means selecting only required columns into DTO/view model instead of loading full entity.

// Bad: loads all columns
var users = await context.Users.ToListAsync();

// Good: loads only required columns
var users = await context.Users
    .AsNoTracking()
    .Where(x => x.IsActive)
    .Select(x => new UserDto
    {
        Id = x.Id,
        Name = x.Name,
        Email = x.Email
    })
    .ToListAsync();
Short Answer: Projection reduces selected columns, DB IO, network payload and memory usage.
What to say: “In production, I avoid returning EF entities directly. I project to DTOs using Select. This also avoids over-fetching sensitive/unnecessary fields.”

8. Joins, Left Join and GroupJoin

Inner Join

var data = from o in context.Orders
           join c in context.Customers on o.CustomerId equals c.Id
           select new
           {
               OrderId = o.Id,
               CustomerName = c.Name
           };

Left Join

var data = from o in context.Orders
           join c in context.Customers on o.CustomerId equals c.Id into customerGroup
           from c in customerGroup.DefaultIfEmpty()
           select new
           {
               OrderId = o.Id,
               CustomerName = c != null ? c.Name : "No Customer"
           };

GroupJoin

var data = context.Customers
    .GroupJoin(context.Orders,
        customer => customer.Id,
        order => order.CustomerId,
        (customer, orders) => new
        {
            CustomerName = customer.Name,
            OrderCount = orders.Count()
        });

Select vs SelectMany

// Select: returns collection of collections
var orderLists = customers.Select(c => c.Orders);

// SelectMany: flattens all orders into single sequence
var allOrders = customers.SelectMany(c => c.Orders);

Any vs Count

// Better for existence check
bool exists = await context.Users.AnyAsync(x => x.Email == email);

// Avoid for existence check because it counts all matching rows
bool exists2 = await context.Users.CountAsync(x => x.Email == email) > 0;

10. EF Loading: Eager, Lazy, Explicit

Eager Loading

var orders = await context.Orders
    .Include(o => o.Customer)
    .Include(o => o.OrderItems)
    .ToListAsync();

Loads related data in same query or split queries. Good when you know related data is required.

Lazy Loading

Related data loads automatically when navigation property is accessed. Can cause N+1 issue if not controlled.

Explicit Loading

var order = await context.Orders.FirstAsync(x => x.Id == orderId);
await context.Entry(order).Collection(x => x.OrderItems).LoadAsync();

11. N+1 Problem

N+1 happens when one query loads parent records and then one separate query runs for each parent to load child data.

// Risk with lazy loading
var orders = context.Orders.ToList(); // 1 query
foreach (var order in orders)
{
    Console.WriteLine(order.Customer.Name); // N additional queries
}

Fix with Include / Projection

// Include fix
var orders = await context.Orders
    .Include(o => o.Customer)
    .ToListAsync();

// Projection fix - often best for APIs
var orders = await context.Orders
    .Select(o => new OrderDto
    {
        OrderId = o.Id,
        CustomerName = o.Customer.Name
    })
    .ToListAsync();
What to say: “When I see multiple DB calls in logs for a list API, I suspect N+1. I fix it using projection or Include and verify generated SQL.”

12. How EF Generates SQL

EF Core takes LINQ expression tree, translates it using database provider into SQL, parameterizes values, sends SQL to database, reads result and materializes objects/DTOs.

var query = context.Users
    .Where(x => x.City == "Delhi")
    .Select(x => new { x.Id, x.Name });

string sql = query.ToQueryString(); // See generated SQL in EF Core
Short Answer: EF converts LINQ expression tree to SQL through provider like SQL Server provider and executes it when query is materialized.
What to say: “For performance issues, I inspect generated SQL using ToQueryString or logging, then check indexes and execution plan.”

13. ACID, Transactions and Isolation

ACID Properties

PropertyMeaningBank Transfer Example
AtomicityAll or nothingDebit and credit both succeed or both rollback
ConsistencyData remains validTotal balance rules remain valid
IsolationTransactions should not incorrectly impact each otherTwo transfers should not corrupt balance
DurabilityCommitted data remains savedAfter commit, transfer remains even after crash

EF Core Transaction Example

using var transaction = await context.Database.BeginTransactionAsync();
try
{
    fromAccount.Balance -= amount;
    toAccount.Balance += amount;

    await context.SaveChangesAsync();
    await transaction.CommitAsync();
}
catch
{
    await transaction.RollbackAsync();
    throw;
}

Isolation Levels

  • Read Uncommitted: Allows dirty reads.
  • Read Committed: Prevents dirty reads; common default.
  • Repeatable Read: Prevents non-repeatable reads.
  • Serializable: Strongest isolation, but may reduce concurrency.
  • Snapshot: Uses row versioning to reduce blocking.
What to say: “For financial operations, I treat debit and credit as a single transaction. If any step fails, rollback ensures atomicity.”

14. Concurrency Handling

Optimistic Concurrency

Assumes conflicts are rare. EF checks RowVersion/Timestamp during update.

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
    public byte[] RowVersion { get; set; }
}
modelBuilder.Entity<Product>()
    .Property(p => p.RowVersion)
    .IsRowVersion();
try
{
    await context.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    // Reload database values, compare, show conflict message or retry
}

Pessimistic Concurrency

Locks data during transaction. Useful where conflict risk is high, but can increase blocking/deadlocks.

What to say: “For normal business apps I prefer optimistic concurrency using RowVersion. For high-risk financial inventory updates, we may use transaction plus proper isolation/locking.”

15. How to Fix Slow Query

Short Answer: Check generated SQL, add proper indexes, use projection, avoid N+1, apply pagination, remove early ToList, and review execution plan.

Step-by-Step Senior Approach

  1. Reproduce the slow API/query.
  2. Enable EF SQL logging or use ToQueryString.
  3. Check if query is filtering in DB or memory.
  4. Check if full entity is loaded instead of DTO projection.
  5. Check missing indexes on WHERE/JOIN/ORDER BY columns.
  6. Check N+1 queries in logs.
  7. Use pagination for large result sets.
  8. Check DB execution plan for scan vs seek.
  9. Use compiled query for very hot repeated queries if required.
  10. Use caching for stable read-heavy data where appropriate.
// Before: heavy query
var users = await context.Users.Include(x => x.Orders).ToListAsync();

// After: optimized for API list
var users = await context.Users
    .AsNoTracking()
    .Where(x => x.IsActive)
    .OrderBy(x => x.Id)
    .Skip((page - 1) * size)
    .Take(size)
    .Select(x => new UserListDto
    {
        Id = x.Id,
        Name = x.Name,
        OrderCount = x.Orders.Count()
    })
    .ToListAsync();

16. LINQ/EF Performance Checklist

  • Keep query as IQueryable until final execution.
  • Use AsNoTracking for read-only data.
  • Use projection with Select into DTO.
  • Apply Where filters before ToList.
  • Use Any instead of Count > 0 for existence.
  • Use pagination with OrderBy.
  • Avoid N+1; use Include or projection.
  • Avoid loading large navigation graphs unnecessarily.
  • Use indexes for filter, join and sort columns.
  • Check generated SQL with ToQueryString/logging.
  • Use async methods in web APIs: ToListAsync, FirstOrDefaultAsync.
  • Do not expose IQueryable directly from API/controller layer.
  • Be careful with client-side methods that cannot translate to SQL.
  • Use AsSplitQuery for huge Include graphs where cartesian explosion happens.
  • Use compiled queries only for very frequent hot queries.

17. Advanced EF Core Topics for 10+ Years

Global Query Filters

modelBuilder.Entity<User>()
    .HasQueryFilter(x => !x.IsDeleted);

Useful for soft delete and multi-tenant filtering.

Compiled Queries

private static readonly Func<AppDbContext, int, Task<User?>> GetUserById =
    EF.CompileAsyncQuery((AppDbContext ctx, int id) =>
        ctx.Users.FirstOrDefault(x => x.Id == id));

Useful for high-frequency queries, but not needed for every query.

Single Query vs Split Query

var data = await context.Orders
    .Include(x => x.OrderItems)
    .AsSplitQuery()
    .ToListAsync();

Split query helps avoid cartesian explosion when including multiple collections.

Raw SQL

var users = await context.Users
    .FromSqlInterpolated($"SELECT * FROM Users WHERE City = {city}")
    .ToListAsync();

Use parameterized raw SQL when LINQ cannot express an optimized query.

Repository and Unit of Work

DbContext already behaves like Unit of Work. Repository can be useful for abstraction, but avoid over-generic repository that hides IQueryable optimization.

Migrations

EF migrations manage schema changes. In production, review generated SQL before deployment.

18. Final Interview Q&A Script

Q1. How do you optimize LINQ query?

Short: Use IQueryable, filtering at DB level, projection, AsNoTracking, pagination, proper indexes, avoid N+1 and early ToList.
Say this: “I optimize LINQ by making sure query execution happens in database, not memory. I keep query as IQueryable, apply Where, OrderBy, Select projection and pagination before ToListAsync. For read-only APIs, I use AsNoTracking. If still slow, I check generated SQL, execution plan and indexes.”
var result = await context.Users
    .AsNoTracking()
    .Where(x => x.IsActive && x.City == city)
    .OrderBy(x => x.Id)
    .Skip((page - 1) * size)
    .Take(size)
    .Select(x => new UserDto { Id = x.Id, Name = x.Name })
    .ToListAsync();

Q2. Explain IQueryable vs IEnumerable with example.

Short: IQueryable executes query at DB/provider level. IEnumerable works on in-memory collection.
Say this: “In EF, IQueryable is preferred until query is fully built because it translates to SQL. If we convert to IEnumerable or ToList too early, remaining filters run in application memory.”
// DB filtering
var q = context.Users.Where(x => x.IsActive); // IQueryable
var users = await q.Where(x => x.City == "Delhi").ToListAsync();

// Memory filtering after ToList
var allUsers = await context.Users.ToListAsync();
var delhiUsers = allUsers.Where(x => x.City == "Delhi");

Q3. How to fix slow query?

Short: Inspect SQL, execution plan, indexes, projection, pagination, N+1, and client-side evaluation.
Say this: “First I check generated SQL and DB execution plan. Then I verify indexes on filter/join columns, remove unnecessary Include, apply DTO projection and pagination, and ensure no ToList is called before filters.”
var sql = context.Users
    .Where(x => x.Email == email)
    .ToQueryString();

Q4. How to handle concurrency?

Short: Use optimistic concurrency with RowVersion; handle DbUpdateConcurrencyException.
Say this: “For most applications, I use optimistic concurrency with RowVersion because conflicts are rare. If another user updates the same row, EF throws concurrency exception and we can reload values, show conflict or retry based on business rules.”

Q5. Explain ACID with real example.

Short: ACID ensures reliable transaction: all-or-nothing, valid data, isolated operations and permanent commit.
Say this: “In bank transfer, debit from one account and credit to another must happen in one transaction. If credit fails after debit, transaction rollback protects consistency. After commit, data should survive crash.”

Q6. How pagination improves performance?

Short: It returns only required page records instead of entire dataset.
Say this: “Pagination reduces DB work, network payload and memory usage. In APIs and grids, I always use OrderBy with Skip/Take. For very large data, I consider keyset pagination.”

Q7. Explain projection importance.

Short: Projection fetches only required columns into DTO.
Say this: “Projection is one of the biggest optimizations. Instead of loading full entity with all columns and navigation properties, I select only what API response needs. It also prevents exposing sensitive fields.”

Q8. What is N+1 problem?

Short: One query for parent plus N queries for child records.
Say this: “N+1 usually happens due to lazy loading. For a list of 100 orders, it may execute 1 query for orders and 100 queries for customers. I fix it using Include or better projection.”

Q9. Tracking vs NoTracking?

Short: Tracking is for update; NoTracking is for read-only performance.
Say this: “EF tracking keeps entity state for SaveChanges. It is useful when I update entity. For read-only APIs and reports, tracking is unnecessary overhead, so I use AsNoTracking.”

Q10. How EF generates SQL?

Short: EF translates LINQ expression tree to SQL using provider and executes on materialization.
Say this: “EF does not execute LINQ immediately. It builds expression tree, database provider translates it to SQL, parameters are generated, and execution happens on ToListAsync/FirstAsync/CountAsync. I can inspect SQL using ToQueryString.”

19. Quick Revision Cheat Sheet

  • AsNoTracking: Read-only query performance.
  • Projection: Select only required columns.
  • Pagination: Skip/Take with OrderBy; keyset for huge data.
  • IQueryable: DB-side execution.
  • IEnumerable: In-memory execution.
  • Deferred Execution: Query executes on iteration/materialization.
  • Immediate Execution: ToList, Count, Any, First.
  • N+1: Many queries due to lazy loading; fix with Include/projection.
  • ACID: Atomicity, Consistency, Isolation, Durability.
  • Transaction: Commit all or rollback all.
  • Concurrency: RowVersion and DbUpdateConcurrencyException.
  • Slow Query: SQL, execution plan, index, projection, pagination.
  • EF SQL: Expression tree translated by provider.
  • Any vs Count: Use Any for existence.
  • First vs Single: First returns first; Single expects exactly one.
  • Include: Load navigation data carefully.
  • SplitQuery: Avoid cartesian explosion with multiple collections.
